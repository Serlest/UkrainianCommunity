4 сентября 2026 года. Облачный этап завершён: проверенные сценарии прошли на настоящих Firebase Auth, Firestore, Functions и Storage, в том числе через iOS SDK на Simulator. Это продолжение [заключительного локального аудита](IOSFinalReleaseAudit-2026-09-04.md); прежний пункт о выключенном тестовом billing закрыт.

## Что сделано и что найдено

С разрешения пользователя к существующему `uac-android-test-20260903` подключён открытый платёжный аккаунт Firebase Payment. Созданы отдельная Firebase iOS app и Storage bucket в `europe-west3`, развёрнуты 23 функции подготовленного пакета и проверенные Rules. Существующий доступ Android в тестовом проекте сохранён. Включена защита Storage через App Check; режимы Firestore/Auth не ужесточались. Identity Platform не обновлялся, рабочие аккаунты и их двухэтапная проверка не использовались.

**В настоящем облаке найден реальный источник ошибки прав:** первоначально старая загрузка фото возвращала 403. У нового Storage service agent отсутствовало разрешение читать Firestore для проверки Storage Rules. Добавлена стандартная роль `roles/firebaserules.firestoreServiceAgent` только служебному аккаунту тестового Storage. После этого те же Rules и тот же разрешённый пользователь смогли загрузить и прочитать фото. Изменять права пользователей или код релиза не потребовалось. В production эта служебная роль уже присутствует — подтверждено отдельным чтением.

Firebase CLI в использованном неинтерактивном режиме пропускает автоматическую проверку этой связи. Поэтому в дальнейшую подготовку облака нужно включать явную проверку IAM и настоящую загрузку, а не только успешное развёртывание Rules. Зависимость Storage Rules от доступа к Firestore описана в [документации Firebase](https://firebase.google.com/docs/storage/security/rules-conditions#enhance_with_firestore); назначение роли — в [справочнике Google IAM](https://docs.cloud.google.com/iam/docs/roles-permissions/firebaserules).

## Первоначальные отказы и их завершение

Все первоначальные логи и xcresult сохранены. Помимо исправленного IAM:

- Первое развёртывание потребовало явного разрешения retry для триггера; затем при первом создании облачной инфраструктуры возникли конфликт создания служебного bucket и задержка доступности Eventarc service agent. Чтение облака обнаружило только 16 ACTIVE вместо 23, несмотря на код завершения CLI 0. Повторно развёрнуты только 7 недостающих функций, затем подтверждены все 23.
- Временной iOS-копии сначала не хватало корневого Info.plist; копирование исправлено. Сборка с отключённой подписью получила ошибку Keychain; обычная подпись Simulator устранила её.
- Проверка старого загрузчика ошибочно ожидала исходные JPEG-байты, хотя он намеренно повторно сжимает изображение. Для старого пути проверены декодирование, размеры и сохранённый MIME; новый путь по-прежнему проверен побайтово.
- Ручной запуск уборки сначала был отклонён, потому что расписание приостановлено. Возобновлено только тестовое расписание фото, выполнен один вызов, затем оно снова приостановлено; настройка уборки выключена в завершающем блоке скрипта.

После устранения этих причин все три итоговых iOS xcresult содержат Passed / 1 passed / 0 failed / 0 skipped. Неуспешные предварительные запуски не посчитаны успешными.

## Что делать перед выпуском

1. Подготовить совместимое развёртывание ограниченного серверного пакета в production: сверить текущие Rules, IAM, регион и конфигурацию; сохранить старые API и оставить новые команды/уборку выключенными. Для production используется отдельный iOS-кандидат, не полный тестовый файл с соседней Android-работой.
2. После развёртывания прочитать реальные версии функций/Rules и проверить прежний путь на контролируемых данных. Облачная проверка выше закрывает тестовый проект, но не заменяет эту проверку production.
3. Собрать основной iOS-проект с новым уникальным номером и подписью, загрузить в TestFlight, проверить принятую сборку. Временную staging-копию не использовать. Публикация в App Store остаётся отдельным шагом.
4. Включать новые команды сначала для контрольных аккаунтов и действий, проверить доступ и выключение уже на нужном сервере; расширять аудиторию после подтверждения. Историческую массовую уборку фото не включать вместе с первым запуском новых прав.
5. До публичного выпуска сверить действующую анкету App Privacy с фактическими данными приложения. Предыдущая попытка чтения анкеты потребовала входа; этот пункт не закрыт облачными тестами.

Серверное переключение подготовлено для конкретных действий организации и галереи. Оно поможет исправлять политику этих действий без нового iOS-релиза после установки поддерживающей сборки. Все разрешения iOS и любые будущие клиентские ошибки таким способом вынести на сервер нельзя. Уже опубликованная версия продолжает использовать свои старые пути.
