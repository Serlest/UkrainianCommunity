# iOS: завершение локального плана и подготовка релиза

Этот документ дополняет первый пакет `IOSAccessReliability-2026-09-04.md`. Production не изменён. Облачная и физическая проверка относится к следующему этапу подготовки релиза.

## Закрытие оставшихся пунктов реализации

| Пункт исходного плана | Реализация и доказательство |
|---|---|
| Различать причины отказа | `organizationAccessDiagnostics.ts` выдаёт безопасный `reasonCode` и случайный `correlationId`; журнал содержит действие, версию клиента, исход и длительность. Нет UID, названий, пользовательского текста, URL и изображений. iOS показывает украинское/немецкое объяснение для роли, аккаунта, почты, сессии, конфликта, отключённого маршрута, лимита, сети и неизвестного результата |
| Сравнение старых и новых прав | Клиент пакетно передаёт реально использованные прежние решения; сервер сравнивает их со своими и пишет `organization_access_comparison`. Эти сведения помечены `client_reported` и не дают никаких разрешений. Контракт прежних 1 080 решений сохранён |
| Включение отдельных действий | `actionModes`, `commandModes`, список тестовых UID и стабильный процент охвата. Верхний `mode: shadow` отключает новые маршруты. Сервер проверяет переключатели повторно при записи. Новые медиа-команды всегда требуют явного включения |
| Проверка отката | На Emulator проверены включение сохранения для выбранного аккаунта, выключение, запрет новой серверной записи после выключения. В Swift проверено возвращение к прямому маршруту, отсутствие обхода при `permission-denied`, отклонение ответа старого UID |
| Безопасная замена фото галереи | `saveOrganizationPhoto`: сервер сохраняет новый неизменяемый JPEG, проверяет актуальную роль и ожидаемый прежний URL, затем одной транзакцией меняет метаданные и сохраняет результат операции. Два редактора не перезаписывают друг друга. Счётчик при замене не растёт |
| Уборка незавершённых загрузок | Незавершённая операция истекает через 24 часа; файл поступает в очередь уборки ещё с 24-часовой отсрочкой. Опубликованное изображение не удаляется. Удаление использует точное поколение Storage и повторяется при временной ошибке |
| Старые незавершённые загрузки | Отдельно включаемый ограниченный проход по 250 объектам с курсором. Для файлов старше семи дней отсутствие основной записи подтверждается транзакцией; блокирующая запись не позволяет позднему старому запросу вновь прикрепить удаляемый файл. Проверяются ссылки фотографии и логотипа/обложки организации |
| Понятная ошибка в редакторе | Ошибка находится внутри открытой формы фото. При конфликте выбранный файл и подпись остаются в редакторе. Замена доступна через меню фотографии в управлении организацией |

Серверная загрузка принимает JPEG до 3 MB; Base64 увеличивает тело примерно на треть. Это ниже лимита HTTP-запроса Functions второго поколения. Условия записи/удаления по поколению подтверждены документацией [Google Cloud Storage](https://docs.cloud.google.com/storage/docs/request-preconditions); лимит запроса — [Cloud Run functions quotas](https://docs.cloud.google.com/functions/quotas). Настоящее время передачи и стоимость нужно измерить в тестовом облаке: длительности Emulator не заменяют эти измерения.

## Совместимость и границы

- Старые API и Storage-пути сохранены. Новые файлы находятся в `organizations/{id}/photoVersions/{operationHash}.jpg`; действующие Rules уже разрешают их чтение по прежней видимости организации и запрещают клиентскую запись/удаление. Дополнительные чтения документов в Storage Rules не добавлялись.
- При выключенном новом маршруте новый клиент использует прежнее добавление фото. Отказ сервера в доступе не переключает запись на старый API. Неизвестный итог повторяется с прежним operation ID.
- Двухэтапная защита v1 не усилена. Новая фото-команда сохраняет проверку, которая раньше выполнялась при загрузке в Storage. Она не создаёт обход существующего требования к защищённому аккаунту.
- Квитанции фото живут 30 дней после завершения/истечения; удаление аккаунта анонимизирует автора операции и сохраняет возможность закончить уборку. Старые незавершённые загрузки не удаляются автоматически сразу после публикации функции: очистка имеет отдельные выключенные по умолчанию переключатели.
- Уборка относится к каноническим записям галереи и полям изображений организации. Произвольные копии старых download URL в чужих текстах/внешних сайтах не являются отдельными владельцами файла; удаление и замена фотографии могут прекратить доступ по прежней ссылке.
- Миграция остальных прямых операций новостей/событий остаётся постепенной архитектурой, а не обязательной полной переписью перед этим релизом. Нынешние Rules продолжают защищать старые клиенты.

## Конфигурация

Документ только для сервера: `serverConfiguration/organizationAccess`. Отсутствующий документ означает прежний режим.

Начальное состояние после публикации серверов:

```json
{"mode":"shadow","commandsEnabled":false,"photoCleanupEnabled":false,"legacyPhotoSweepEnabled":false}
```

Пример для выбранного тестового аккаунта — подставить его реальный UID в отдельной тестовой среде:

```json
{
  "mode": "enforced",
  "commandsEnabled": true,
  "enabledUserIds": ["TEST_ACCOUNT_UID"],
  "rolloutPercent": 100,
  "actionModes": {
    "editInfo": "enforced",
    "resubmitRequest": "enforced",
    "managePhotos": "enforced"
  },
  "commandModes": {
    "updateOrganizationInfo": "enforced",
    "saveOrganizationPhoto": "enforced"
  },
  "photoCleanupEnabled": true,
  "legacyPhotoSweepEnabled": false
}
```

Если `actionModes` задан, не перечисленные действия остаются в `shadow`. Удаление списка `enabledUserIds` допускается только при намеренном расширении аудитории; процент затем ограничивает её стабильно по UID. Переключатели выбирают маршрут, но не дают роли. Для отката задать `mode: shadow`, `commandsEnabled: false`; функции и квитанции не удалять. Завершение ранее созданной уборки регулируется отдельным `photoCleanupEnabled`, независимо от маршрута новых записей. Исторический проход включается отдельно после проверки кандидатов и совместимости.

## Серверный пакет

К списку первого пакета добавлены `saveOrganizationPhoto` и `cleanupOrganizationPhotoLifecycle`. Также повторно включить в узкий пакет `getOrganizationAccess`, `updateOrganizationInfo`, `createOrganizationPhotoMetadata`, `deleteOrganizationPhotoMetadata`, `deleteOwnAccount` с их новыми зависимостями. Не публиковать весь текущий рабочий каталог Functions: в проекте остаются другие независимые изменения.

Для production ограничения полей отмены применяются отдельным уже подготовленным Rules-патчем. Сами Firestore/Storage Rules в этом дополнении не расширялись. Новые тесты доказывают запрет клиентской записи в серверные квитанции, задачи очистки и новые файлы даже для владельца платформы.

Перенос фиксируется в кратком результате и контрольных суммах задачи. Тесты интерфейса используют изолированные данные; системный выбор изображения проходит через настоящую медиатеку Simulator. На снимке успешной замены галерея использует тестовый URL-заглушку, а соседняя команда организации не подключена: это доказательство работы редактора/метаданных и счётчика, не реальной загрузки изображения из production. Хранение файла и смена URL отдельно проверены на Firebase Emulator.

## Проверки перед релизом

Это оставшиеся внешние проверки, а не скрытая локальная реализация:

1. Развернуть выбранный пакет в отдельном тестовом облаке с выключенными маршрутами. Проверить настоящий Auth, App Check и IAM Storage; запись активного пользователя и отказ постороннему.
2. На поддерживаемых старых установках проверить обычное редактирование, повторную заявку, загрузку/удаление фото, отмену события и согласия. Ошибку служебной даты в старых сборках нельзя исправлять ослаблением Rules.
3. Включить действия для тестовых UID; проверить потерю сети/ответа, отзыв роли во время загрузки, два редактора, очистку, затем выключение и восстановление маршрута. Измерить задержку и частоту отказов по действию/версии.
4. На физическом iPhone проверить Face ID, фон/возврат, смену аккаунта, настоящую доставку push, отмену/перенос события. Симулятор проверяет локальную очередь, но не APNs и биометрический датчик.
5. Подготовить новый build, архив, TestFlight, материалы обновления и проверку App Store. Номер сборки и опубликованное приложение этой работой не менялись.

Итоговые локальные результаты и контрольные суммы находятся в `implementation/finalization/evidence/` текущей задачи; краткий итог — в `implementation/RESULT-IOS.md`.
