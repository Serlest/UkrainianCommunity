# Функциональный аудит Android относительно iOS 1.2 (107)

Дата: 14 октября 2026. **Аудит № 1 завершён как исследование; функциональный паритет и безопасность production-сценариев пока не сертифицированы.** Визуальный аудит и общий аудит готовности к Play не выполнялись в рамках этой работы.

## Эталон и смысл отметок

- iOS: исходник `release/1.2-107` на `1332693`. `git diff` не обнаружил различий в дереве `UkrainianCommunity/` Android-ветки относительно этого коммита. Сравнивались доступные функции iOS Build 107; работа приложения на живом iPhone в этот день не проверялась.
- Android: ветка `codex/android-parity-1.2-107`, исходная точка этого аудита `dda702e`. Последний подтверждённый предыдущей документацией Play Internal артефакт — Build 86; актуальное состояние Play Console здесь не читалось. Описанный ниже паритет относится к текущему **исходнику**, пока не загруженному в Play.
- **S** — подтверждено синтетическим Android → staging → серверным чтением в предыдущем шаге 8; **L** — текущие локальные/эмуляторные проверки и код; **К** — реализация обнаружена, но требуемый сквозной сценарий не пройден; **Н** — iOS-функция в Android отсутствует или намеренно только для чтения. Ни один статус не означает проверки production-базы или личного устройства.

## Проверка контракта общей базы

1. `Firebase/firestore.rules`, `Firebase/storage.rules` и индексы не изменялись относительно iOS 107 в этой ветке. Из исполняемых файлов `functions/src` изменились только `passkeyOrigins.ts`, его тест и два вызова проверки origin в `passkeys.ts`: без staging-переменных production RP/origin остаются прежними. В ветке также изменены staging-конфигурация и вспомогательные скрипты. Никакого production deploy или записи в production Firestore в ходе аудита не было.
2. Android привязывает Auth/Firestore/Storage/Functions к проверенной Firebase app identity; проверяет текущий UID перед личными действиями. Прямые записи профиля ограничены self-editable полями; новости/организации используют серверные правила и/или авторизованные callable. Это защита по коду и тестам, а не гарантия отсутствия ошибки во всех ещё не выполненных сценариях.
3. Текущий тест Rules: **203 pass, 0 fail, 1 skip**. Пропущенный `bannerMeasurementJourney` требует отдельного Auth/Functions эмулятора; он был пройден отдельно в шаге 6, но не является staging доказательством. Серверные unit: **443 pass, 0 fail, 95 skip** (пропущены integration suites без их отдельного окружения). Отдельно теперь прошли Directory **2/2**, organization workflow **25/25**, platform role **1/1**, content-planning **3/3**, FID cleanup **1/1**.
4. Android JVM: свежий запуск с `--rerun-tasks` — **1 972 pass, 0 fail/skip**. На чистом API 37 при масштабе текста 1.0 четыре функциональных UI-suite дали **8/8**: лента, редактор Справочника, очередь баннеров, регистрация/комментарии в изолированных UI-сценариях. Эти UI-тесты используют фикстуры/fake backend и не доказывают серверную доставку.
5. Живой изолированный staging `uac-android-test-20260903`: `firebase functions:list` вернул **41 ACTIVE** функцию. Android-протокол разрешает **72** имени; **41** из них отсутствует на staging, в том числе регистрация событий, комментарии, owner/role actions, публикация контент-плана, FCM test и объявления. Все 72 имеют экспорт в локальном серверном исходнике. Это ограничение **тестового развёртывания**, не доказательство отсутствия функций в production. Слепое развёртывание всех функций и запуск привилегированных записей не выполнялись.
6. Предыдущий staging прогон шага 8 прошёл с двумя одноразовыми аккаунтами; созданные тестовые аккаунты/документы были удалены и прочитаны обратно как отсутствующие. Его точные границы описаны в [отчёте шага 8](AndroidParity107Step8E2E-2026-10-14.md). В этом аудите новых staging-данных не создавалось.

## Что требуется для функционального принятия перед визуальным аудитом

1. **Вернуть недостающие iOS-пути на Android:** DSA подача/решение/апелляция с теми же валидацией, правами, ревизиями и идемпотентностью; управление редакторами Справочника; owner управление юридическими документами и общий список evidence; очистка inbox. Для `writeClientDiagnostic` определить согласованный Android контракт и ограничения приватности. Каждый путь проверить на эмуляторе и на изолированном staging, не через production-данные.
2. **Довести staging до проверяемого состояния:** по одному ревьюировать и разворачивать необходимые callable из точного commit, подтверждать `ACTIVE` и привязку к изолированному проекту. Добавить тестовые роли/данные, пройти позитивные и негативные сценарии Android UI → callable/Rules → точный server read-back, затем очистку. Для DSA и владельческих действий нужны безопасные тестовые кейсы и реальный MFA-эквивалент; обход защиты ради зелёного теста недопустим.
3. **Закрыть реальную доставку и медиа:** FCM регистрация/доставка/tap/отказ/отзыв, загрузка и удаление фото, баннерное изображение и квитанции показа/клика с дедупликацией, офлайн-очереди и смена аккаунта. Проверить отсутствие чужих записей и сохранение iOS-читаемого формата.
4. **Проверить личный Android и общую систему:** существующий аккаунт, Google/Apple/passkey по доступной конфигурации, TOTP владельца, реальные письма и правовой re-accept; затем iOS и Android читают одни и те же безопасные staging-документы после Android-записей. Для production до записи требуется отдельный read-only инвентарь активных Rules/Functions/индексов; локальная сборка его не заменяет.

**Решение аудита:** текущий Android исходник содержит большую часть обычных и административных модулей, но полного функционального паритета с iOS 107 нет. Функциональную приёмку нельзя закрыть по имеющимся доказательствам. Визуальный аудит начинается только после отдельного разрешения пользователя; он не подменит перечисленные функциональные проверки.
