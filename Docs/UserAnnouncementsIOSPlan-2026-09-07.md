# Оповещения пользователей — общая архитектура, первый запуск на iOS

Дата: 2026-09-07. Статус: продуктовые решения согласованы в обсуждении; техническая схема предложена для реализации.

Этот документ фиксирует требования и последовательность работ. Создание документа не означает начало реализации, запуск сборок, подключение платного перевода, изменение Firebase production или публикацию релиза.

## 1. Назначение и границы

Владелец UAC создаёт адресные объявления из раздела «Оповещения пользователей» в своём профиле. Примеры: просьба проверить обновление и отправить отзыв через «Звернення», предупреждение о технических работах, информационное сообщение.

Первый запуск интерфейса и доставки — только iOS; следующий этап должен поддержать Android без переписывания серверной функции. Модели, API, аудитория и состояние объявления общие для обеих платформ с самого начала. Включение платформ — настройка выпуска, а не отдельные реализации рассылок. Серверные изменения не должны менять поведение существующих уведомлений Android или iOS. Объявление о работах не является полноценным режимом обслуживания: экран, работающий при недоступности основного сервера, — отдельная задача.

## 2. Согласованные требования

| Область | Решение |
| --- | --- |
| Отправитель | Только владелец приложения; администраторы приложения и организаций не могут создавать или отправлять объявления |
| Аудитория | Конкретные зарегистрированные пользователи и/или несколько групп, объединённых без дублей |
| Основные группы | Все пользователи; зарегистрированные; гости; владельцы организаций; администраторы приложения; администраторы организаций |
| Гости | Все, кто сейчас пользуется без входа, в том числе вышедшие из аккаунта |
| Регион | Вся Австрия или несколько федеральных земель; для зарегистрированных — регион аккаунта, не фильтр просмотра и не регион организации |
| Гости и регион | Все гости без регионального ограничения, в том числе в смешанной аудитории |
| Содержание | Заголовок и текст на украинском и немецком |
| Перевод | По кнопке через сервер; результат редактируется и проверяется владельцем до отправки |
| Основной показ | Окно при открытии приложения или подходящем возвращении в него |
| Push | Независимый переключатель «Дополнительно отправить push» |
| Режим один раз | После показа/закрытия автоматических повторов нет; сообщение доступно в истории |
| Режим подтверждения | «Ознакомился» или «Позже»; повтор при следующем открытии, максимум раз за сеанс, до подтверждения или истечения срока |
| Хранение подтверждения | В аккаунте зарегистрированного пользователя; на устройстве гостя |
| Действие | Необязательная кнопка «Написать через звернення» с темой объявления |
| Управление | Черновики, предпросмотр, тест себе, немедленная/отложенная отправка, срок действия, история и прекращение дальнейшего показа |
| Статистика | Показ окна, подтверждение и переход к обращению отдельно от результатов отправки push |

## 3. Рабочие правила для реализации

Ниже — предлагаемые технические уточнения. Они не подменяют согласованные решения и могут уточняться при первом пакете.

### Адресация

- Выбранные группы и персональные UID объединяются через OR, затем к зарегистрированным применяется региональный фильтр. Предпросмотр явно показывает исключённых из-за региона персональных получателей.
- «Все пользователи» означает зарегистрированную часть плюс гостей. При выбранной Вене предпросмотр пишет: «Аккаунты с регионом Вена + все гости без ограничения региона».
- Если регион аккаунта отсутствует, пользователь входит в «Всю Австрию», но не в отдельную землю. Регион не выводится из города, GPS или организации.
- Роли приложения и членство в организациях проверяются сервером по актуальным авторитетным данным. Один человек с несколькими организациями учитывается один раз.
- Поддержку модераторов организаций можно включить после проверки фактической модели членства. Произвольный конструктор новых групп в первую версию не входит.
- Предлагается вычислять право на просмотр по текущему аккаунту/ролям/региону в течение срока действия. Для push аудитория фиксируется при запуске рассылки; новые подходящие пользователи увидят окно, но не получают повторную массовую отправку.
- После входа/выхода и смены аккаунта очищаются очередь и кэш личных объявлений; право просмотра пересчитывается. Нельзя показывать текст предыдущего аккаунта.
- Объявления для гостей по природе доступны любому человеку без входа. В гостевую выдачу нельзя включать персональные тексты, списки UID или административные данные кампании.
- В интерфейсе число аккаунтов и число доступных push-устройств показываются отдельно. Общее число всех гостей заранее неизвестно; не выдавать число установок за число людей.

### Показ, повторы и действия

- Активность определяется серверными `startsAt`, `expiresAt`, статусом и правом просмотра. Время хранится в UTC, в форме отображается с явным часовым поясом Europe/Vienna.
- После первой загрузки должны показываться актуальные непоказанные объявления, полученные во время отсутствия пользователя.
- Предлагаемая граница сеанса: холодный запуск или возврат после не менее 30 минут в фоне. Короткое переключение приложений не вызывает повтор. Порог вынести в отдельную политику с тестами.
- Только одно окно одновременно. Не перекрывать вход, MFA, обязательные документы, системные разрешения и уже открытое модальное действие. Остальные объявления доступны списком, без последовательной очереди навязчивых окон.
- Для режима один раз сохранять `presentedAt` после фактического появления окна. Не считать получение данных показом. Для подтверждения отдельно хранить `acknowledgedAt`; открытие push, «Позже», закрытие и переход к обращению не равны подтверждению.
- При сбое записи подтверждения сохранить локальное намерение и повторить запись. На другом устройстве до синхронизации возможен повтор; это не следует скрывать обещанием мгновенного подтверждения везде.
- Срок действия завершает автоматический показ и повторы. История остаётся доступной согласно политике хранения. Прекращение показа проверяется при следующей синхронизации; уже доставленный push не отзывается.
- По нажатию push повторно проверить статус и доступ. Для истёкшего/отменённого сообщения показать нейтральное состояние вместо запуска обязательного окна.
- Гостевая история и отметки локальные; переустановка/очистка данных может сбросить их. После входа не переносить гостевое подтверждение автоматически на аккаунт.
- Связать обращение с `announcementId` и подставить тему. До реализации проверить гостевой путь «Звернення»: если нужен вход, сохранить намерение и восстановить его после входа, не теряя контекст.
- При отсутствии сети не обещать получение новых объявлений. Для уже загруженных личных сообщений проверять текущий аккаунт и известный срок; при неизвестной актуальности не открывать обязательное окно автоматически.

### Языки и перевод

- Показать редактируемые поля `uk` и `de`, исходный язык и кнопку перевода на второй язык.
- Переводить только текст объявления. UID, адреса получателей, роли и сегменты не передаются переводчику.
- Существующий заполненный перевод не перезаписывать без явного действия владельца. При изменении исходника помечать второй вариант как требующий проверки.
- Перед отправкой оба языка обязательны; предпросмотр доступен для каждого. Ручное заполнение работает при недоступности сервиса перевода.
- Провайдер, текущая цена, условия обработки текста и способ хранения ключа ещё не выбраны. Проверить перед подключением. Ключ хранится только на сервере; ограничить доступ владельцем, длину запросов и частоту.
- Историю показывать на текущем языке приложения. Для внешнего push проверить наличие серверной языковой настройки устройства/аккаунта; при отсутствии определить явное правило до реализации.

## 5. Предлагаемая архитектура

### Совместимость iOS и будущего Android

Уточнение пользователя: Android будет подключён позже; архитектура должна предусматривать его сейчас, без изменений Android-кода в текущем документальном этапе.

1. Один серверный модуль и один версионированный контракт для всех клиентов: содержание, роли, регионы, сроки, подтверждение, перевод, статистика. Не создавать `iosAnnouncements` и будущую копию `androidAnnouncements`.
2. У объявления `targetPlatforms` с допустимыми значениями `ios`/`android`, а сервер отдельно хранит включённые платформы выпуска. Сейчас разрешена только iOS; позднее владелец сможет выбрать iOS, Android или обе. Старые объявления сохраняют исходную аудиторию: включение Android не запускает прошлые рассылки автоматически.
3. Регистрация устройства включает платформу, build/version и поддерживаемую версию контракта объявлений. Отсутствие capability означает отсутствие поддержки. Выдача и push проверяют пересечение платформ объявления, включённых платформ выпуска и возможностей клиента. Capability служит совместимости, но никогда не заменяет авторизацию аккаунта/получателя.
4. Старые приложения не должны получить новое окно или маршрут, который не умеют обработать. Для новых объявлений использовать отдельную выдачу; не записывать их вслепую в общий legacy inbox, который читают старые клиенты. Общий экран истории нового клиента объединяет старый inbox и разрешённую выдачу объявлений. Возможность безопасной записи в inbox допустима только после доказанной фильтрации всех старых читателей.
5. Подтверждение хранится один раз на аккаунт и объявление, без включения платформы в ключ. Если позднее объявление адресовано обеим платформам, подтверждение на iPhone останавливает повторы на Android после синхронизации. Для отдельных просьб проверить каждую платформу создаются отдельные объявления.
6. Статистика уникальных аккаунтов общая; платформу события можно использовать для разбивки, не суммируя её как уникальных людей. Гостевые отметки остаются на каждой установке.
7. Доставка push использует общий подбор получателей и существующий транспорт с отдельными платформенными адаптерами. В локальном `functions/src/notifications/pushRegistrations.ts` уже есть группировка iOS/Android и `messageForAndroid`; перед подключением проверить её контракт, не добавлять параллельную копию транспорта.
8. SwiftUI и Compose реализуют свои экраны поверх одной серверной семантики. Общие JSON-примеры контрактов и сценарии переходов проверяются сервером, Swift и позднее Kotlin. Не требуется переносить UI или вводить новый кроссплатформенный фреймворк.
9. Изменения добавочные: новые поля optional/с безопасными defaults, отдельные endpoints, независимые переключатели UI/выдачи/push. Отключение новой функции не затрагивает уведомления организаций, ролей и обращений.
10. При добавлении Android серверный контракт остаётся прежним: клиентский repository, Compose-экраны, локальные гостевые отметки, регистрация capability, contract/UI/device tests и затем включение Android. Если всё же требуется новый контракт, поддерживать прежнюю версию в переходный период.

### Сервер

Отдельный модуль `functions/src/announcements/` с валидатором, подбором аудитории, жизненным циклом, выдачей, отметками и переводом. Имена ниже — проектные, не существующие API.

- `announcements/{id}`: закрытый управляющий документ; `schemaVersion`, `targetPlatforms` (при первом запуске `[ios]`), автор, две локализации, аудитория, режим показа, действие, сроки, revision, статус.
- Статусы публикации: `draft → scheduled/active → expired/cancelled`. Прогресс доставки push хранить отдельно (`pending/running/completed/partial/failed`), чтобы сбой push не выключал окно.
- После публикации контент и адресацию не менять на месте: отмена и новое объявление. Это сохраняет смысл подтверждения конкретной версии текста.
- Owner-only операции: создать/изменить черновик, предпросмотр аудитории, перевод, тест себе, опубликовать/запланировать, отменить, прочитать статистику. Право проверяется сервером при каждой операции; клиент не пишет итоговые статусы напрямую.
- Отдельная выдача только разрешённых полей зарегистрированному получателю; гостям — только объявления с гостевой аудиторией. Административный документ целиком клиентам не отдавать.
- `users/{uid}/announcementReceipts/{id}`: `presentedAt`, `acknowledgedAt`, `actionOpenedAt`, revision. Запись серверными операциями с проверкой получателя; временные метки сервера, повторные запросы идемпотентны.
- Интегрировать историю аккаунта на уровне нового клиента через стабильный ID объявления; не выдавать новые записи старым читателям legacy inbox. Для объявления должен существовать один путь запуска push, чтобы inbox-trigger и задача объявления не отправляли его дважды.
- Сегментация, индексы, пагинация и пакетная доставка должны работать без загрузки всех пользователей в один вызов. Повтор задачи не создаёт новые inbox-записи или намеренные повторные push. Абсолютную доставку push «ровно один раз» не обещать.
- Счётчики показов и подтверждений строить по уникальным отметкам; принятие push провайдером не означает прочтение или фактическое отображение на телефоне.
- Запланированные отправки проверяют отмену, срок и текущий статус до каждой партии. Предпросмотр аудитории — оценка на момент проверки; при запуске состав может измениться.

### Гости и push

Гостевое окно — отдельная выдача активных общедоступных объявлений с локальными отметками. Не требовать регистрации аккаунта только ради объявления.

Для дополнительного push гостям нужна отдельная регистрация установки и безопасный переход `guest ↔ account`. Это обязательный пакет для полного заявленного охвата, а не уже имеющаяся возможность. До его завершения нельзя объявлять доставку гостевых push готовой.

Проверить текущий транспорт, разрешения, App Check и способ удостоверения установки. Клиент не может зарегистрировать чужой токен, получить чужую адресную рассылку или произвольно увеличить статистику. После выхода удалить связь с аккаунтом; гостевой push не должен содержать остатки персонального сообщения. Учесть уже находящийся в доставке push: использовать нейтральный внешний текст для адресных сообщений, проверять доступ при открытии.

Гостевая статистика — по установкам и приблизительна. Локальные подтверждения не выдавать за проверенные подтверждения конкретных людей.

### iOS

- Раздел владельца: список → редактор → аудитория → предпросмотр двух языков/охвата → тест себе → финальная отправка.
- Модели, repository и view model объявлений, внедрённые через существующие зависимости приложения.
- Отдельная политика показа объявлений, согласованная с текущим popup coordinator; не менять глобальное поведение всех critical-уведомлений.
- Гостевое локальное хранилище, история без входа и очистка личного состояния при смене аккаунта.
- Явная поддержка iOS в выдаче и доставке. Не полагаться только на скрытый пункт меню или значение platform от недоверенного клиента для защиты адресного текста.
- Dynamic Type, VoiceOver, прокрутка длинного текста, обе локализации, светлая/тёмная тема.

## 7. Критерии приёмки

1. Владелец может отправить тест только себе. Администратор приложения, администратор организации, обычный пользователь и гость не могут отправлять, переводить или читать закрытую аудиторию прямым API-вызовом.
2. Вена в аккаунте + Тироль в фильтре просмотра → пользователь получает венское объявление. Регион организации не влияет. Аккаунт без региона не получает региональное объявление.
3. Смешанная аудитория «зарегистрированные Вены + гости» работает именно так; пересечение нескольких ролей не создаёт дублей.
4. Актуальное сообщение, отправленное при закрытом приложении, появляется после открытия. Режим один раз не повторяется; «Позже» допускает повтор только в новом сеансе; «Ознакомился» синхронизируется между устройствами аккаунта.
5. Выход/вход/смена аккаунта не раскрывают личное сообщение и не смешивают подтверждения. Гость получает только общедоступную гостевую часть.
6. Запрет системных push не мешает получить окно. Разрешённый push открывает нужное объявление с повторной проверкой доступа. На Android новые объявления не выдаются и push этой функции не отправляются.
7. Срок, отмена и повтор фоновой задачи корректны; незавершённая партия может быть продолжена без дублей inbox. Уже доставленный push не считается отозванным.
8. Обе локализации доступны и проверены; смена языка меняет язык истории. Автоперевод не публикует сообщение сам и не уничтожает ручные правки без действия владельца.
9. Переход в обращение сохраняет тему объявления; переход, подтверждение ознакомления и отправленный отзыв остаются разными событиями.
10. Показ фиксируется при отображении окна, а не загрузке данных; повторные события не увеличивают уникальные показатели. Гостевые установки и аккаунты не объединяются в счётчик «людей».
11. Не нарушены существующие уведомления о ролях, обращениях, организациях, аккаунте и документах. Обязательные экраны сохраняют приоритет.
12. Push на реальном iOS-устройстве, гостевые разрешения, смена пользователя и открытие из завершённого приложения подтверждены отдельно от локальных тестов и сборки.
13. Старые iOS/Android-клиенты без capability не получают новые записи в legacy inbox и неподдерживаемые push-маршруты; существующие уведомления работают как прежде.
14. Контракт допускает Android без копирования серверной логики. В контрактных тестах подтверждение одного аккаунта на двух платформах общее; выключенный Android исключён из доставки. Включение Android не расширяет аудиторию уже опубликованных iOS-объявлений.

## 8. Нерешённые технические зависимости

- Провайдер перевода, стоимость и условия обработки текста — выбрать после проверки актуальных условий, до подключения.
- Гостевой push: удостоверение установки, хранение токенов, поведение разрешений и очистка связи с аккаунтом — проверить в A01, реализовать в A05.
- Источник серверной языковой настройки, точные источники членства/владения организациями и гостевой путь обращений — проверить в A01.
- Срок хранения истории/отметок, удаление аккаунта, агрегированные метрики и лимиты размера/частоты — согласовать с существующими механизмами хранения до завершения A02.
- App Check/MFA использовать согласно проверенной политике проекта; не копировать автоматически настройки диагностического push-вызова.
- Фильтр по версии приложения полезен для просьб проверить обновление, но пока остаётся расширением после первой версии.

## 9. Границы проверки и выпуска

Реализация начинается отдельным следующим шагом с A01. Локальная проверка не означает готовность Firebase production, APNs или App Store. Подключение платного сервиса, production deployment, релизная сборка/TestFlight и публикация выполняются как отдельные явно согласованные действия. Android-файлы и посторонние рабочие изменения не входят в этот план.
