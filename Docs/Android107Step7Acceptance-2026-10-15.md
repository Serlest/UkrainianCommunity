- Play Console по-прежнему показывает Build **86 (1.1)** в Internal и Closed Test; нового кандидата не загружали. - В production Firebase Android **нет SHA-1**, а скачанная конфигурация не содержит Android OAuth-клиента Google. Play App Signing SHA-1 из публичного сертификата Play: `19:5C:20:74:D2:AE:61:33:21:84:B3:71:50:24:8B:CA:DF:9C:CB:A5`; upload SHA-1 в Play: `A7:B6:47:4D:70:8E:F3:E5:72:4B:AD:25:F0:58:6D:D3:02:B1:AE:35`. Это настройка для проверки перед Google-входом в Play-сборке, а не выполненная production-правка.
- Staging Firebase Android имеет SHA-1 и Android OAuth-клиент; тестовый APK показывает кнопку Google. Его повторный Google-вход после offline вернул ошибку и с временным App Check debug token; на эмуляторе отсутствует Google-аккаунт. Причину успешностью клиента не подменять.

Живой production `assetlinks.json`: HTTP 200, JSON, правильные два SHA-256 и **только** `delegate_permission/common.handle_all_urls`. Перед включением production passkey добавить `delegate_permission/common.get_login_creds`, сохранив действующую связь ссылок, затем прочитать опубликованный файл и пройти вход на Play-доставленной сборке.

## Ворота на исходной контрольной точке шага 7

Это постзагрузочная приёмка, не условие до создания кандидата.

## Дополнение: эмуляторная проверка и решение владельца

Владелец уточнил: физический Android есть, но его ручная проверка состоится **после установки беты из Google Play Internal Testing**. Поэтому отсутствие USB-отладки на корпоративном Samsung больше не является условием остановки перед подготовкой Play-кандидата. Физическая приёмка переносится после доставки беты; её результат нельзя заранее считать успешным.

На чистом `UAC_Step8_API37_Fresh` (API 37, шрифт 1.0) установлен локальный APK SHA-256 `409a02f226ee066bd62a65f8c261267b1e1fe210b2bccb451d755753c7379064`. Экранные проверки: вход и системный Photo Picker **5/5**, UI TOTP и языкового шлюза **7/7**, экранный паритет на синтетических данных **1/1**. Это 13 пройденных UI-тестов, без подмены реальных Auth/FCM/Play сценариев. Полный локальный JVM-набор **1 998/1 998**, `lintLocalDebug` прошёл.

Отдельный старый `MainVisualParityJourneyUiTest#actualMainScreensKeepAccessibleChromeAcrossLanguageThemeAndSystemFont` дважды завершился ошибкой `browse-list` отсутствует: он пытается открыть ленту при гостевой сессии, а реальный `MainActivity` показывает обязательный вход. Это несовместимая предпосылка теста, а не доказательство дефекта ленты. Тест не засчитан; его следует привести к авторизованному fixture либо убрать дублирование с `Step7VisualParityUiTest`. На прежнем API 26 AVD установка APK зависла; после остановки этого AVD тот же APK успешно запустился на чистом API 37. Совместимость API 26 текущим прогоном не подтверждена.

На исходной контрольной точке перед Play-бетой оставались cloud-конфигурация production Android App Check, SHA-1/Google OAuth, выбор включаемых Apple/passkey путей и `get_login_creds` на production-домене. Для полного staging E2E требовались актуальные Storage Rules/индексы/выбранные callable. Обновлённое состояние этих пунктов — ниже. Подписанный AAB, загрузка в Internal Testing и проверка Play-подписи относятся к отдельно разрешаемому шагу 8; ручной тест владельца следует **после** получения этой сборки.

Production AAB-скрипт получает Firebase project/app/bucket из текущей Firebase-конфигурации, но `UAC_PRODUCTION_GOOGLE_WEB_CLIENT_ID` не выводит автоматически. В проверенном shell все четыре переменные upload-подписи и флаги Google/Apple/passkey отсутствовали; это не доказывает отсутствие ключа в защищённом хранилище Mac. Проверка существующего upload key и выбор флагов принадлежат шагу 8.

Развёрнуты ровно 32 недостающих Android callable; **80/80** имён allowlist активны. Production Rules/индексы не трогали.
- Полный `Android/scripts/test-community-staging.mjs` на API 37 прошёл: экранная регистрация и отмена события, комментарий, согласие и отзыв аналитики, просмотр новости, согласие и отзыв измерения баннера, экранные impression/click, дедупликация, запреты доступа, серверный read-back и очистка одноразовых аккаунта/документов/баннера/Storage. - Тест ожидания комментария теперь сообщает `actionError` вместо общего тайм-аута. Ожидание клика баннера привязано к опустевшей очереди отправки: холодный старт callable занял более пяти секунд, поэтому фиксированная задержка не доказывала отправку. Скрипт регистрирует путь синтетической регистрации до запуска UI, чтобы убрать его и при ошибке теста. Это изменения проверки и очистки, а не обход backend-правил.
- В production Firebase Android добавлены оба SHA-1 из Play Console, сохранены прежние два SHA-256; скачанная Firebase-конфигурация теперь содержит Android OAuth-клиенты. Google-вход на устройстве после доставки Play-беты ещё не проверен.

Сохранены **15/15** прежних файлов по исходным хешам и конфигурация; добавлен только `/.well-known/assetlinks.json` с `common.get_login_creds` при сохранении `common.handle_all_urls`. Все шесть прочитаны как ACTIVE с этим origin и прежним production RP ID. Сервер по-прежнему принимает iOS/web origin. Путь passkey на Play-подписанном устройстве пока не проверен.
