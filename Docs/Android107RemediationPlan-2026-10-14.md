# Android → уровень iOS 1.2 (107): план исправлений

Дата: 14 октября 2026. Основа: [функциональный аудит](Android107FunctionalAudit-2026-10-14.md), [визуальный аудит](Android107VisualAudit-2026-10-14.md), [общий аудит/Play](Android107OverallParityPlayAudit-2026-10-14.md). Рабочая ветка `codex/android-parity-1.2-107`. Изолированный Firebase для проверок: **только** `uac-android-test-20260903`; production-данные и Play в этом плане не меняются автоматически.

Правило выполнения: один шаг за раз. После каждого шага — конкретные изменения, результаты положительных и отрицательных проверок, серверный read-back, остаточные ограничения, коммит/синхронизация; следующий шаг начинается только после разрешения владельца. Проверка эмулятора и staging не заменяет проверку физического телефона и Play-сборки.

## Шаг 1: журнал выполнения

- Добавлены owner-only экран и маршрут для `decideDsaCase`/`decideDsaAppeal`; форма показывает факты, правовую/договорную основу, территорию, срок и способ обжалования. Решение требует отметки о человеческом рассмотрении и отдельного подтверждения.
- Источник перечитывает `feedback` только с сервера, сверяет актуальную роль и второй фактор, запрещает прямое клиентское чтение канонических `dsaCases`. Перед отправкой повторно сравнивает ревизию и проекцию; после ответа сверяет серверную проекцию. При неопределённом результате не делает автоматического повтора записи.
- Локальные проверки: Compose UI 2/2; полный JVM-набор 1 985/1 985; функции `lint`/`build` и 14 целевых серверных тестов; Android lint прошёл. На staging выборочно опубликованы только `decideDsaCase` и `decideDsaAppeal`.
- На staging API 26 пройдены настоящий TOTP владельца и Android UI для **трёх исходов дела**: `noAction`, `restricted`, `removed`. Ограничение и удаление выполнялись только после заранее подготовленного соответствующего состояния синтетической новости; server read-back подтвердил один результат в каноническом `dsaCases` и клиентской проекции `feedback`.
- После решения заявитель подал апелляцию через действующий callable. Android UI владельца прошёл оба исхода: `upheld` закрыл апелляцию, `changed` вернул дело к новому рассмотрению и удалил текущую проекцию решения. Отдельно проверены отказ обычному пользователю и CAS-отказ при устаревшей ревизии. Android не получил прямого доступа к `dsaCases`.
- Одноразовые `feedback`, `dsaCases`, `news`, Auth-аккаунты, уведомления `notificationInbox`, публичные профили и системные журналы удаляются по точным маркерам. После обнаружения старой неполной очистки удалены четыре её уведомления и четыре публичных профиля. Повторный поиск по маркерам после финальных прогонов показал **ноль** оставшихся уведомлений и публичных профилей; удаление основных документов и Auth-аккаунтов подтверждалось чтением после каждого прогона.
- Ограничения: живой владелец и iOS-приложение на том же кейсе не участвовали; использовались одноразовые синтетические данные изолированного проекта. Физический Samsung блокирует режим разработчика политикой администратора. Дополнительный совмещённый прогон `removed` → `upheld` не завершился: на общем AVD одновременно устанавливался BordKompass, и Android test APK застрял на установке до запуска UAC. Основной исход `removed` и оба исхода апелляции проверены отдельно; совмещённый сценарий следует повторить на свободном устройстве в шаге 7. Эти границы не подменяют подтверждённый staging-контракт шага 1.

**Статус шага 1:** техническая приёмка завершена; владелец разрешил шаг 2.

## Шаг 2: журнал выполнения

- Android получил owner-only маршрут и экран «Редакторы довідника / Ratgeberredakteure»: текущие гранты, поиск и пагинация зарегистрированных пользователей, выдача и подтверждённый отзыв. Список и квитанция после записи читаются с сервера; транзакция отвергает изменившийся `grantedAt`, повторную выдачу и неактивную цель. Экран скрыт от чужой роли; клиент дополнительно проверяет действующего владельца с привилегированным MFA, а Firestore Rules остаются главным барьером записи.
- Формат общей базы сохранён как в iOS 107: `directoryEditors/{uid}` содержит только `enabled`, `grantedBy`, `grantedAt`; отзыв удаляет документ. Найдена и исправлена ранее скрытая ошибка Android: `saveDirectoryCategory`/`deleteDirectoryCategory` отсутствовали в разрешённом списке callable, поэтому редактор не мог опубликовать материал, хотя локальные UI-тесты проходили. Для `saveDirectoryCategory` задан бюджет запроса выше серверного максимума payload 800 КБ; неопределённый результат записи не повторяется автоматически.
- На staging `uac-android-test-20260903` выборочно развёрнут только существующий `searchManagedUsers`; серверные Rules и Functions производства не менялись. Сквозной прогон на API 26: обычная роль получила отказ от экрана и серверной записи; владелец с настоящим TOTP выдал грант через Android UI; редактор вошёл в Android и изменил тестовую категорию; сервер прочитал ревизии 1 и 2 и оба документа `versions`; устаревшая ревизия получила `ABORTED`; владелец отозвал грант через Android UI, после чего редактор получил `PERMISSION_DENIED` при новой публикации.
- Финальный прогон после удаления временной диагностики повторил все четыре Android UI-сценария и серверный read-back. Локально прошли экранные тесты 2/2, Directory Rules 5/5, серверные Directory integration 2/2 и полный Android JVM-набор 1 987/1 987. Три одноразовых Auth-аккаунта, пользовательские/публичные профили, грант, категория и обе версии удалены с чтением после удаления; временный App Check debug token отозван, повторный список показал ноль токенов этого прогона.
- Граница: iOS 107 не хранит отдельный журнал *выдач и отзывов* редакторских прав; проверенная история и ревизии относятся к публикации категорий. Android сохранил общую iOS-схему без нового журнала грантов. Живые аккаунты, физический телефон и production-база в шаге 2 не участвовали.

**Текущий статус:** техническая приёмка шага 2 завершена; шаг 3 не начат и требует отдельного разрешения владельца.
