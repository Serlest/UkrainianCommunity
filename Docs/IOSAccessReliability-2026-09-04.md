## Совместимость и включение

1. Сначала загрузить в отдельное тестовое облако перечисленные ниже функции. Проверить настоящие Auth/App Check, получение и отзыв ролей, создание заявки с обязательными согласиями, загрузку фотографий и push на физическом iPhone. Локальный Emulator использует тестовые Auth-токены; это не доказательство работы живого Identity Platform или APNs.
2. Сохранить снимок действующих функций и Rules. Разворачивать только выбранные функции; массовый `firebase deploy --only functions` для этого пакета не подходит: в исходном проекте есть другие незавершённые изменения.
   Отдельно применить узкое ограничение полей отмены события. Оно уже находилось в локальном проекте до этой работы и проверено вместе с Rules. Из него подготовлен `implementation/evidence/event-cancellation-only.rules.patch` без соседнего Android-изменения. Сверить его с актуальными live Rules перед применением. Пока это ограничение не опубликовано, прямой обход штатной отмены в production остаётся возможным.
3. Оставить `serverConfiguration/organizationAccess` отсутствующим либо `{mode: "shadow", commandsEnabled: false}`. Документ закрыт для прямого доступа приложений. Новые чтения не меняют разрешения. Существующие 53/65/67 продолжают пользоваться прежним протоколом. Дефект даты в старых 53/65 нельзя исправить ослаблением защиты служебных полей: для них нужен более новый клиент.
4. Развернуть `getLegalEvidencePage` до выпуска нового iOS: новый полный экспорт зависит от этой функции. Запрос аналитики V2 переходит на старый формат только если новая функция отсутствует. Серверные отказы доступа не вызывают обход через старую запись.
5. После проверки серверов выпустить отдельный новый iOS build. Номер текущего приложения и находящийся на проверке build 67 этим пакетом не изменялись.
6. В тестовой среде, затем для согласованного production включения выставить `{mode: "enforced", commandsEnabled: true}`. Новые клиенты получают решения сервера и используют команду сохранения организации. Старые остаются на Rules. Не отключать их прямую запись, пока они поддерживаются.
7. Откат: вернуть `shadow` и `commandsEnabled: false`; новые клиенты возвращаются к прежнему маршруту после обновления конфигурации. Не удалять новые функции и квитанции во время отката. Не откатывать исправления отзыва аналитики и незавершённые отмены: старый код вновь разрешил бы повторные ошибки.

Для будущих изменений роли и разрешения на данные уже можно менять на сервере. Этот пакет переносит туда также решения интерфейса по девяти действиям организаций и безопасное сохранение организации. Прямые записи новостей/событий ещё контролируются Rules; изменение их разрешений требует согласования серверной модели с Rules, но не новой версии iOS для уже известных действий. Новые виды действий и разрешения самой iOS (камера, уведомления, Face ID) могут потребовать обновления приложения или решения пользователя. Обещать отсутствие любых будущих ошибок нельзя; защита от повторения — единый контракт и обязательные проверки совместимости.

## Узкий список серверного развёртывания

`getOrganizationAccess`, `updateOrganizationInfo`, `updateAnalyticsConsent`, `updateAnalyticsConsentV2`, `trackAnalyticsEvent`, `listLegalEvidenceAccounts`, `getLegalEvidencePage`, `cancelEvent`, `completeEventCancellationOnCreate`, `createOrganizationPhotoMetadata`, `deleteOrganizationPhotoMetadata`, `deleteNews`, `deleteOrganization`, `clearMyFeedback`, `deleteFeedback`, `deleteMyFeedback`, `clearFeedbackInbox`, `clearSystemLogs`, `deleteSystemLog`, `cleanupExpiredData`, `deleteOwnAccount`.

Условия аутентификации исправляемых v1-функций сохранены относительно выгруженного production-кода. Это явно зафиксировано `legacyCallableContext.ts`; для удаления своего аккаунта сохранены недавний вход и запрет удаления владельца платформы/организации. Нельзя заменять этот совместимый guard общим строгим helper без отдельного решения о MFA. Новая команда организации сохраняет требования существующих прямых Rules.

Новые запросы сохранения организации, фотографий и согласия привязаны к ожидаемому UID. При смене аккаунта во время ожидания сервер отвергает несовпадение; старые варианты запросов остаются совместимыми. В legacy fallback аналитики сохраняется старый четырёхполевой формат.

Новые квитанции команды и завершённой отмены живут 30 дней и удаляются существующим ежедневным retention-заданием. Отмена хранит только необходимые заголовки и получателей до завершения, затем удаляет их; незавершённые задания не удаляются по возрасту. Политика удаления аккаунта дополнена новыми ссылками.
